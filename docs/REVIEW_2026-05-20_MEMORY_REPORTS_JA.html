M6.25 / memory subsystem / 統合レビュー

2026 Agent Memory 調査資料の統合レビュー

M6.25 メモリサブシステム設計の前提となる 2 本の調査資料を、非実装者でも読みやすい形に整理した 日本語レビュー。元 Markdown は変更せず、両資料の役割の違い、ベンチマークの位置づけ、 mew に入れるべき memory 設計の結論、recall / write / injection / scoring の流れを統合して示す。

1. Executive summary

結論を 4 行で

  • 2026 の主流は「巨大 context」でも「会話履歴を vector DB に入れる」でもなく、typed memory + lifecycle (write-manage-read) + provenance + bounded retrieval + downstream task 評価。
  • mew の最初の判断は raw transcript は memory ではない、recall は native tool として始める、常時 prompt injection は v0/v1 では避ける。
  • 書き込みは「毎ターン自動 append」ではなく candidate queue + kind 別 approval gate。memory は evidence であって next-action authority ではない。
  • 評価は LoCoMo / LongMemEval だけでは不足。MemoryArena / LongMemEval-V2 / AMA-Bench / STATE-Bench で「memory が後続行動に効いたか」を見る。ただし mew の 合否判定は Harbor-style coding fixtures が担う。

2 本の調査資料は、同じ 2026 年メモリ研究の地図を別の角度から描いている。 本文書では先に両者の役割と差分を示し、次に mew への落とし込み (memory 種類、書き込み・読み出しの流れ、評価指標) を整理する。

実装上の目標形は次のとおり。

small, typed, approved, cited, scoped, stale-aware memory

逆に避けるべき形は次のとおり。

large, self-written, prompt-injected, universal memory

3. mew に入れるべき memory 設計の結論

72103 の Executive Finding と 72630 の「実用寄り」整理は同じ方向を指す。M6.25 の設計判断としては以下を採用する。

採用すべき形

  • Raw transcript は provenance であって memory ではない。 append-only / content-addressed で保存し、durable memory として直接 recall させない。
  • MemorySystem.recall() は native tool として始める。 v0/v1 では prompt injection (常時注入) を避ける。injection は PromptSectionRegistry 経由の将来課題。
  • Durable memory は typed entry。 kind / scope / source_refs / proof_refs / validity_state / invalidators / supersedes / contradicts を持つ。
  • Graph memory は主ストアではなく、bounded traversal の retrieval seed 拡張に限る。 edge は derived_from / supersedes / contradicts / same_task_shape / failure_cluster / file_symbol / reviewer_correction / preference_scope 等で型付け。
  • Write は automatic append ではなく candidate queue + kind 別 approval。 revise は「approved candidate を消費する」操作のみで、モデルが直接編集する API は出さない。
  • 評価は Harbor-style coding fixtures を主にし、MemoryArena / LongMemEval-V2 / AMA-Bench / STATE-Bench を補助に使う。 LoCoMo / LongMemEval は sanity check 止まり。
  • memory は evidence であって next-action authority ではない。 system policy / tool access / task contract / verifier 出力 / fresh repo evidence を上書きしてはならない。

推奨されるアーキテクチャ境界

Native provenance (transcript / tool / verifier)
   └── 直接 recall 不可

Candidate extraction
   ├─ event-triggered (session close / verifier / reviewer / 失敗反復)
   └─ typed candidate + source/proof refs

Approval / write gates (kind 別)
   └─ scope / contradiction / freshness / privacy / utility

Durable MemoryStore
   └─ typed entries + revision lineage + invalidators

Indexes
   └─ exact / path / symbol / tag (+ optional vector / typed graph)

MemorySystem
   ├─ recall  : read-only evidence retrieval
   ├─ revise  : approved candidate 消費のみ
   ├─ project : 将来用の bounded prompt projection
   └─ trace   : observability / scoring

MemoryToolProvider           PromptSectionRegistry
  ├─ provider 側 schema       └─ injection は将来分離
  └─ MemorySystem に委譲          (ToolRegistry とは別)

このうち MemoryToolProvider が policy を持たない、ToolRegistry は callable schema だけ、injection は別 registry、という分離が肝。DESIGN_2026-05-20_M6_25_MEMORY_SYSTEM_TOOL_PROVIDER.md の方向と一致する。

4. やるべきこと / まだやらないこと

V0 → V1 → V2 を 72103 から圧縮した上で、72630 の hype 警告を重ねた。

段階スコープ

段階 目的 含めるもの 含めないもの
V0 memory 境界と trace skeleton を作る (動作は無くてよい) MemorySystem 注入インタフェース、明示的に enable した場合のみ read-only recall、EmptyMemorySystem、stable 入出力 schema と schema hash、trace event、provenance と durable memory の分離。 prompt injection、モデル可視の write、graph traversal。
V1 bounded recall が役立つことを autonomous write 無しで実証 project-scope の承認済み durable entry、手動 / レビュアー承認の seed、kind は episodic_task / project_fact / failure_shield / reviewer_correction、exact/path/symbol/tag 検索、stale/superseded フィルタ、Harbor fixtures での memory on/off 比較。 automatic durable write、prompt section projection、self-evolving retrieval、unbounded graph recall。
V2 反復作業を承認付き durable advantage に変える event-triggered candidate extraction、kind 別 approval gate、typed graph edges、seed 後の bounded chain recall、procedural repair memory (強い proof 要件)、file hash / verifier command / task contract / reviewer veto に紐づく stale、scoring dashboard (write precision / stale recall / memory-attributable wins / 反復失敗ブロック数)。 高信頼 preference / convention の 小さな prompt projection は late-V2 のオプションに留め、まだ既定にはしない。offline consolidation も late-V2 オプション。

禁則 (まだやらない)

やる

  • Raw provenance を append-only / content-addressed で保管。
  • recall を read-only native tool で先に提供。
  • kind 別 approval gate と revision lineage (superseded_by / contradicted_by / stale_due_to) を持つ。
  • graph traversal は depth/fanout/token budget 付き、drop reason を残す。
  • Harbor fixtures で memory on/off 比較を取る。
  • scoring dashboard を JSONL でも良いから出す。

まだやらない

  • 毎ターン自動の durable write。
  • raw transcript / 古い tool 出力 / 古いモデル文の prompt 直挿入。
  • memory に next-action 決定権を持たせること。
  • ToolRegistry に memory storage / graph policy / prompt projection を持たせること。
  • user / project / task / procedural を 1 つの global vector store にまとめること。
  • project 情報を user-scope memory 経由で他プロジェクトに漏らすこと。
  • 失敗 / 思弁的 trajectory からの procedural memory 昇格 (verifier/reviewer proof 無し)。
  • limit 無しの graph 展開、drop telemetry 無しの memory 拡張。
  • v1/v2 の observability / regression gate より先に EvolveMem 的 self-evolution を有効化すること。
  • LoCoMo / LongMemEval のみで M6.25 を採否判定すること。
  • native recall trace で usefulness を確認する前に prompt projection を入れること。

5. ベンチマークの位置づけ

72630 が世代マップ、72103 が mew relevance 付きの利用ガイドを与えている。両者を統合すると、ベンチマークは「会話 recall」「能力分解」「agentic action」「production reliability」「safety」の 5 層で見るのが妥当。

世代と狙い

世代 代表 中心の問い mew での使い方
会話 recall LoCoMo, LongMemEval 長期会話の事実・時間・更新を答えられるか retrieval / indexing の sanity check のみ。採否判定には使わない。
長大 context 耐性 BEAM 10M token 級でも壊れないか スケールストレス用。優先度は低い。
能力分解 MemoryAgentBench, StructMemEval, MemBench retrieval / TTL / forgetting / 構造化を能力単位で測れるか generic memory lifecycle と graph/structured 判断の補助。
agentic action MemoryArena, AMA-Bench, LongMemEval-V2 memory が後続行動・workflow・experience に効くか mew に最も近い generic 評価。非コーディング領域での比較に使う。
production reliability STATE-Bench memory が enterprise タスクの成功率 / 信頼性 / UX を上げるか peer-reviewed ではないので参考扱い。観測のみ。
safety / drift MemEvoBench, EvoMemBench, Evo-Memory misevolution / poisoning / stale drift self-evolving 系を導入する前に必ず参照。今は監視対象。

MemoryArena と LongMemEval-V2 の位置づけ

MemoryArena (arXiv:2602.16313)

interdependent な multi-session タスクで、前 session で得た memory を 次の行動に使えるかを評価する 2026 型 benchmark。LoCoMo / LongMemEval で高得点でも、agentic setting では弱いことを示している点が重要。
mew にとっては generic 評価の橋渡し。「recall できる」と「memory が次の tool choice / repair / verification を改善する」の差を見るのに使う。
ただし memory governance / 編集 / 所有権 / 削除 / privacy は主対象でない点に注意。

LongMemEval-V2 (arXiv:2605.12493)

web 環境の workflow / gotchas / premise awareness を覚える「経験豊富な同僚」型の評価。
mew の resident coding advantage の比喩に近いが、コーディング fixture そのものではないため、Harbor を代替するものではない。

Harbor との役割分担

  • LoCoMo / MemBench / MemoryAgentBench → generic memory 系の sanity check
  • MemoryArena / LongMemEval-V2 / AMA-Bench / STATE-Bench → 非コーディング領域での memory 効用比較
  • Harbor-style coding fixtures → M6.25 の合否判定

mew の product claim は coding resident advantage。最終判断は Harbor 側でしか出せない。

mew で測るべき指標

層 指標
generic memory quality Recall@k / MRR、evidence hit rate、stale recall rate、contradiction rate、abstention accuracy、token / latency / API call overhead、write precision、write recall、invalidation latency
mew downstream 同形タスク再実行での改善幅、memory on/off の verifier pass rate、first useful action latency、time to first edit、failure-shield による反復失敗ブロック数、reviewer rescue edits、pass@1 / pass^N、memory-attributable win rate、novel-task canary regression、prompt size / memory projection size、recall tool 呼び出し数と useful-recall ratio

6. Memory 種類の整理

72103 が示す mew 向け taxonomy を中心に、72630 のパターン分類を補助情報として並べる。各 kind は 書き込みゲート、古さ意味、recall budget が異なるため、汎用 working/episodic/semantic/procedural を直に晒すよりこの 8 区分が実装に近い。

Kind 目的 初期ストア 書き込みゲート Recall 経路
provenance 監査・リプレイ・抽出元 (memory ではない) append-only な transcript / tool / verifier ログ memory としてのゲート無し。provenance 記録のみ。 memory として recall 不可。candidate 抽出と監査参照のみ。
working / reentry 今のタスク状態と再入 WorkFrame / lane state / active todo reducer 主導の状態遷移のみ prompt section として供給。durable recall ではない。
episodic 前タスク / 前セッションで何が起きたか 短い episode card + proof refs outcome + verifier / reviewer evidence task shape / file / failure class で recall
semantic プロジェクトの安定的事実・規約 typed fact + source refs + scope contradiction + freshness + approval path / symbol / convention / クエリで recall
procedural 再利用可能な修復手順 / runbook / skill versioned procedure (trigger / action / proof) 強い approval。可能なら検証成功実績。 trigger と現在 evidence で recall
failure-shield 同じ失敗を繰り返さない 失敗試行の要約 + evidence failure 分類 + reviewer approval do_not_repeat evidence としてのみ供給
preference ユーザー嗜好 user-scope の独立ストア 明示的ユーザー承認 or 手動編集 narrow scope projection。project 越境禁止。
graph / symbol memory とコードの関係索引 typed edge + symbol/file key 承認済み entry または決定的 / 静的解析からのみ seed retrieval の後段に bounded 展開

段階表現 (HTML)

1. Raw
provider request/response、tool result、verifier outcome を append-only / content-addressed で保存。memory として直接 recall しない。
▼ event trigger (session close / verifier / reviewer / 反復失敗)
2. Candidate
candidate extractor が typed candidate を作る。fields: candidate_id, memory_kind, scope, source_refs, claim or procedure, trigger_conditions, validity, confidence, utility_score, privacy_class, created_at, last_verified_at, valid_from/until, supersedes/contradicts/derived_from。
▼ kind 別 approval gate
3. Approve
scope / contradiction / freshness / privacy / utility / reviewer or user or policy。失敗側の failure_shield、手順側の procedural は特に強いゲート。in-place 書き換え禁止。superseded_by / contradicted_by / stale_due_to で revision lineage を残す。
▼ Durable に書く
4. Durable
typed entry + revision lineage + invalidators。indexes: exact / path / symbol / tag (+ optional vector / typed graph edges)。stale は時間だけでなく file hash / symbol move / verifier 変更 / contract 変更 / preference 変更 / reviewer 否決 / provider 変更にも紐づく。
▼ model からの recall 要求
5. Recall
request validation → scope/kind filter → exact/path/symbol/tag → (optional) vector → (optional) bounded graph expansion → contradiction/staleness filter → rerank → bounded projection。出力は evidence (id, kind, scope, summary, why_relevant, source/proof refs, validity, confidence, staleness, related ids, dropped_count_by_reason)。instruction / next-action / hidden chain-of-thought を含めない。
▼ (late-V2 のみ) PromptSectionRegistry 経由
6. Inject
高信頼 preference / 活性 convention のみを 小さく projection。ToolRegistry / MemoryToolProvider とは別経路。raw transcript や古いモデル文は決して injection しない。memory は system policy / tool access / task contract / verifier 出力 / fresh repo evidence を上書きしてはならない。
▼ 並列に流れる trace
7. Score
trace event は generic (Recall@k, MRR, stale, contradiction, abstention, write precision, invalidation latency) と mew downstream (verifier pass on/off, pass^N, failure-shield block 数, reviewer rescue, memory-attributable win rate, novel-task canary) を分けて記録。Harbor fixtures が合否判定、MemoryArena / LongMemEval-V2 / AMA-Bench / STATE-Bench は補助比較。

図のレーン番号は実装段階ではなく 責務 の分離を示す。V0/V1 では Recall lane を read-only の native tool に限定し、Inject lane は閉じておく。Score lane は V1 から JSONL で稼働させ、V2 で dashboard に出す想定。
