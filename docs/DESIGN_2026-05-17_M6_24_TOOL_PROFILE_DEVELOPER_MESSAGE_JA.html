Design 2026-05-17 / M6.24 / design only

ToolSurfaceProfile が「ツール定義」と「developer 契約」を同時に所有する設計

この文書は、codex_hot_path の OpenAI/Codex 向けリクエストを Codex CLI に近い形へ寄せるための設計です。生産コードの変更を許可する文書ではなく、 実装時の境界、証跡、レビューチェックを定義します。

対象: implement_v2 / codex_hot_path 追加: role=developer input pre-release: 後方互換不要 禁止: provider-visible finish 復活

要点

1. ただのプロンプト追加ではない

codex_hot_path のツール行動契約は request_body.instructions だけでなく、 role=developer の input item として送る。

2. Profile が一体で所有

Provider-visible なツール schema と、それをどう使うかの developer 契約を 同じ ToolSurfaceProfile snapshot から出す。

3. apply_patch 境界を明示

手動の source edit は apply_patch。 exec_command は inspection、build、test、probe、verification 用。

4. continuation は deferred

現時点では previous_response_id / full retry が継続経路として未整備。 今は full/normal request で role=developer を必ず入れることに集中する。

この設計の判断ポイント: reviewers が provider request JSON を見たときに、OpenAI/Codex の codex_hot_path では role=developer item が存在し、 そこに profile-owned な edit/command 境界が見えること。

1. 何の問題を解くのか

現状の mew は、codex_hot_path で Codex 風の tool name (apply_patch、exec_command など) を出せます。 しかし、そのツールをどう使うべきかという行動契約は request_body.instructions に普通の instruction として混ざっています。

Codex CLI 参照実装では、base instructions、developer instructions、tool schema が分かれています。この設計は、mew 側でもその transport 境界を揃えます。

問題の症状 ツール名は Codex 風だが、行動契約は developer role ではない。
→
具体例 exec_command の heredoc / cat > で source を生成してしまう。
→
修正方針 edit API と shell API の境界を developer role で provider-visible にする。

避けたい drift

tool schema は codex_hot_path なのに、行動契約が別の prompt 由来、古い contract 由来、または instructions-only 由来になる状態。

求める状態

「この profile が公開したツール」と「そのツールの使い方」が同一 snapshot から来たことを hash と metadata で監査できる状態。

2. 現在の mew request と target の違い

変更の中心は request body の置き場所です。base instructions は残せますが、 codex_hot_path の tool behavior contract は OpenAI/Codex では developer-role input item でなければなりません。

現在の mew 形状

instructions

profile prompt sections がここに描画される。tool behavior もここに入る。

input

先頭は raw user task / transcript items。developer item はない。

tools

ToolSurfaceSnapshot.tool_specs から provider-visible tools を lower。

target: Codex-like 形状

instructions

base instructions または lane base。tool behavior の唯一 carrier にしない。

input[0].role = "developer"

同一 profile の developer tool behavior contract。

input[1].role = "user"

codex_hot_path では raw task text。raw task_contract は入れない。

tools

developer contract と同じ snapshot から lower された tools。

Target request の最小イメージ

{
  "instructions": "<base instructions only, or profile-independent lane base>",
  "input": [
    {
      "role": "developer",
      "content": [
        { "type": "input_text", "text": "<rendered codex_hot_path developer contract>" }
      ]
    },
    {
      "role": "user",
      "content": [
        { "type": "input_text", "text": "<raw task text for codex_hot_path>" }
      ]
    }
  ],
  "tools": ["<lowered tools from the same ToolSurfaceSnapshot>"]
}
Codex CLI 参照概念 mew の target
BaseInstructions request_body.instructions。ただし hot-path tool behavior の唯一 carrier にはしない。
developer_instructions ToolSurfaceProfile が選ぶ DeveloperToolBehaviorContract。
build_developer_update_item() {"role":"developer","content":[...]} を作る helper。
router.model_visible_specs() ToolSurfaceSnapshot.tool_specs。
provider-visible finish がない通常 Codex surface mew は internal finish gate を維持し、codex_hot_path に finish tool を出さない。

3. ToolSurfaceProfile が所有するもの

この設計では、ToolSurfaceProfile は tool schema の一覧だけではなく、 それを model にどう使わせるかの developer 契約と、両者が同じ snapshot 由来である証跡を一体で所有します。

selected ToolSurfaceProfile profile_id / profile_version / profile_hash

Provider-visible tools

  • tool names
  • descriptions / schemas / ordering
  • strict/custom lowering policy
  • descriptor hashes

Developer contract

  • role=developer
  • tool behavior rules
  • provider tool names described by the contract
  • content hash / version

Metadata / audit

  • developer contract id
  • transport policy
  • wire visibility
  • fallback reason when applicable
重要: profile_hash は descriptor/spec identity と developer contract identity の両方を覆う必要があります。tool descriptor だけ、または developer contract だけが変わっても hash に反映されないなら不完全です。

Snapshot に追加されるべき代表 metadata

identity

developer_contract_id、developer_contract_version、developer_contract_hash

transport

developer_contract_transport_policy、developer_contract_transport、developer_contract_wire_visible

tool match

developer_contract_provider_tool_names は option 適用後の provider_tool_names と一致。

4. なぜ role=developer が重要なのか

目的は「強い言葉を instructions に足す」ことではありません。 Codex CLI と同じ層に tool behavior contract を置き、provider-visible な request artifact でそれを検査できるようにすることです。

OpenAI/Codex path の必須形

supports_developer_role_input=true かつ provider が OpenAI/Codex なら、request_body.input に role=developer item を含め、 developer_contract_transport=role_developer_input を記録します。

許される fallback は 1 つだけ

provider が developer role を扱えない場合だけ、同じ contract text を instructions に fold し、 developer_contract_fallback_reason=provider_lacks_developer_role を記録します。OpenAI/Codex 実装ではこの fallback を使いません。

5. previous_response_id / developer refresh の扱い

この設計では developer refresh を現時点の実装対象から外します。 理由は、今の mew では previous_response_id 継続が websocket 断で失敗し、 さらに full retry / full replay fallback も未実装だからです。守るべき継続経路がまだないため、 refresh を先に作ると M6.24 の本筋から外れます。

現在の対象 full / normal request を構築する。
→
必須条件 input[0] に role=developer contract を入れる。
→
deferred previous_response_id refresh / full retry は後続マイルストーンで扱う。

今の close gate から外すもの

2 turn 目以降の role=developer refresh、prefix/delta metrics、 previous_response_developer_refresh などは、今回の close gate ではありません。 今回は初回/full/normal request の provider-visible shape を Codex-like に固定します。

今やること

OpenAI/Codex の codex_hot_path request では、raw task の前に profile-owned な role=developer contract を必ず置く。

今やらないこと

websocket 断後の continuation、previous_response_id delta refresh、 full retry / full replay fallback はこの設計の現在実装範囲から外す。

将来の条件

それらを実装する時は、再構築された request や refresh item にも role=developer の行動契約を落とさない。

6. codex_hot_path developer 契約の中身

developer message は短く、運用的であるべきです。WorkFrame、proof、finish gate、 evidence refs、task-specific な closeout pressure は入れません。

最低限含めるルール

  • apply_patch は manual source edits 用。
  • exec_command は inspection、build、test、probe、package-manager setup、verification 用。
  • shell heredoc、cat、printf、sed -i、perl -pi、Python file-writing script などで source を作成・編集しない。
  • shell は build output 作成や tool 実行には使えるが、manual source editing API ではない。
  • write_stdin は既存 exec_command session の poll / interaction 用。
  • optional list_dir が有効なら bounded directory listing 用であることを一文追加。

入れてはいけない内容

  • finish、final_status、summary、evidence_refs、task_done。
  • default hot path にない legacy tool 名: run_tests、run_command、read_file、search_text、glob、inspect_dir。
  • WorkFrame、next_action、required_next、first-write pressure、proof projection、hidden sidecar state。
  • MIPS、Doom、VM、/tmp/frame.bmp、Terminal-Bench など benchmark-specific 文言。

契約文の最小イメージ

You are working through the codex_hot_path tool surface.

Use apply_patch for manual source edits.

Use exec_command for inspection, builds, tests, probes, package-manager setup,
and verification.

Do not create or edit source files with shell heredocs, cat, printf, sed -i,
perl -pi, Python file-writing scripts, or equivalent shell text-generation
shortcuts. Shell commands may create build outputs, run tools, install packages
when permitted, and inspect files, but shell is not the manual source editing
API.

Use write_stdin only to poll or interact with an existing exec_command session
according to the profile's interactive-stdin capability.

7. mew_legacy は混ぜない

mew_legacy は別 profile です。既存挙動を保つか、将来別設計で legacy 専用 developer contract を持つことはできますが、codex_hot_path の契約を流用・merge・部分継承してはいけません。

codex_hot_path

tool names

apply_patch、exec_command、write_stdin、optional list_dir。

developer contract

codex_hot_path_developer_contract_v1 など、同 profile の契約。

mew_legacy

tool names

run_command、run_tests、read tools、legacy finish behavior など。

禁止される混在

legacy request に hot-path contract id を入れない。hot-path request に legacy tool behavior text を入れない。

8. 観測と証跡

現在の observability は維持し、developer contract の metadata を足します。 provider-visible request body がこの設計の主要な acceptance artifact です。

Request artifacts

native-provider-requests.json と provider_request_inventory.json に contract id/hash、transport、 wire visibility、fallback reason、previous-response refresh を記録。

Model-visible sections

profile_developer_contract、raw_task、 native_transcript_delta、task_context_refresh を区別。

Forbidden scan

developer message text も scan 対象。finish/evidence、WorkFrame、proof、 next-action、first-write、sidecar-control、benchmark text を検出。

維持されるもの

provider-native transcript、one-output-per-tool-call pairing、tool routes、 renderer metrics、proof/replay/source snapshot、internal finish gate は維持します。 developer message は request context であり、tool call と transcript pairing の参加者ではありません。

9. Phase 6D.0 から 6D.5

これは 2026-05-14 の Phase 0-5 を置き換えません。Phase 6D は追加の refinement であり、 6D.5 は既存 Phase 5 default-switch gate の再確認です。

Phase 6D.0 - Static Contract Fixture

profile-owned developer contract fixture を追加し、live behavior は変えない。

Close gate: apply-patch/shell-boundary 文を含む。finish/evidence/WorkFrame/proof/next-action/task-specific 文言を含まない。tool names が descriptor fixture と一致。legacy 依存なし。

Phase 6D.1 - Profile Snapshot Ownership

ToolSurfaceProfile / ToolSurfaceSnapshot に contract identity、hash、transport policy、contract tool names を追加。

Close gate: contract 変更で profile hash が変わる。descriptor hash は descriptor-only。request inventory に contract hash。tool names と contract tool names が同じ profile から出る。

Phase 6D.2 - OpenAI/Codex Role Transport

codex_hot_path tool behavior を instructions-only から role=developer input item へ移す。

Close gate: first provider request で input[0].role == "developer"。required boundary text を含む。user task は後続の role=user。transport は role_developer_input。

Phase 6D.3 - Deferred Continuation Handling

previous_response_id developer refresh は今回は実装しない。 現在は full/normal request の role=developer 送信と、 no-developer-role provider fallback だけを扱う。

Close gate: OpenAI/Codex の full/normal request では developer contract が role=developer として存在する。refresh 関連は block 条件にしない。 fallback は provider lacks developer role の場合だけで、OpenAI/Codex fixtures は使わない。

Phase 6D.4 - Legacy Separation And Leak Gates

profile separation と forbidden-surface behavior を証明。

Close gate: legacy request に hot-path contract がない。hot-path に legacy tool 名や finish が default で出ない。developer messages も forbidden scan 対象。internal finish/proof/evidence が developer text に漏れない。

Phase 6D.5 - Behavioral A/B Recheck

fixed tool-surface A/B set と motivating make-doom-for-mips diagnostic を developer-role contract 付きで再確認。

Close gate: request JSON、tool list、route/render records、transcript pairing、proof/source/internal finish artifacts がある。accepted traces に command-edit-boundary violation がない、または default-switch evidence を阻止する。

10. リスクと注意点

contract / tool drift

tool schema と developer contract が別々に更新されると、model-visible な行動契約が実際の tool surface とずれます。 profile hash と tool-name一致テストで防ぎます。

continuation 実装時の contract 消失

今回は previous_response_id / full retry を実装しません。 将来それらを入れる時は、再構築 request や refresh item に role=developer contract を必ず残す必要があります。

provider-visible finish の再混入

この設計は finish tool を戻しません。internal finish gate、proof、sidecar は sidecar-only のままです。

legacy との混在

mew_legacy の tool names や prompt behavior を hot path に混ぜると、比較と監査が崩れます。

shell source authoring

cat > source.c や heredoc で source を生成して外部 reward に通る trace は、 default-switch evidence として clean に扱えません。

過剰な契約文

契約は短く運用的に保つ必要があります。WorkFrame、proof、benchmark 固有文言を入れると別の completion pressure になります。

11. Reviewer checklist

実装レビューでは、以下のどれかが false なら reject する前提です。

OpenAI/Codex の codex_hot_path request に role=developer item がある。 provider request JSON で直接確認できること。
developer message と provider-visible tools が同じ ToolSurfaceProfile snapshot 由来である。 profile hash と metadata が両者の同一性を証明すること。
developer text に required boundary rules がある。 apply_patch manual edits、exec_command inspection/build/test/probe/verification、shell non-authoring boundary。
forbidden text がない。 finish、evidence-ref、WorkFrame、proof、sidecar-control、next-action、first-write、task-specific benchmark language を含まない。
fallback は no-developer-role provider の exact instruction folding だけ。 OpenAI/Codex fixtures は fallback を使わず、fallback reason を記録しない。
mew_legacy が分離されている。 legacy tools と codex_hot_path developer contract を混ぜない。
既存 observability と internal finish gate が維持されている。 transcript pairing、tool rendering、route records、proof/replay/source snapshots、internal gate artifacts を壊さない。
shell-authored synthetic artifact が violation として見える。 make-doom-for-mips 型の cat > / heredoc source authoring は clean default-switch evidence にならない。
